# v2 設計決策記錄（確定性 vs 生成 的邊界）

本檔記錄 v2「確定性引擎 ⊕ 生成式旁白」邊界上的**關鍵決策與其理由**（北極星機制在
[architecture_v2.md](architecture_v2.md)；本檔是「為什麼」）。每條 = 脈絡 / 決策 / 後果。

---

## D1. 「加強 GM output」還是「加強確定性按鈕」？——假二選一

**脈絡**：副本進出靠自由文字＋GM 不可靠（這回合 GM 會輸出工具呼叫、下回合不一定）。
直覺把它變成「a 加強 GM／b 加強按鈕」的取捨。

**決策**：拒絕這個 framing。真正的軸是**「漏掉的代價」**，答案**按代價分兩層**，不是壓一邊：

| 漏掉的後果 | 歸屬 |
|---|---|
| 壞存檔 / 錯數字 / 卡關 | **確定性**（引擎獨佔；GM 在 gate 被擋） |
| 只少一句描述、可事後補 | **GM output**（＋既有 backstop：leveljudge/對帳/dedup） |

**後果**：「什麼都要按鈕」是假命題——符合上排的東西其實很少（副本進出、花錢、解鎖、
閉關、完成任務），而它們**在任何傳統 RPG 本來就是選單動作**。

---

## D2. 沈浸感來自敘事，不來自 GM 寫 state（兩個獨立旋鈕）

**脈絡**：擔心「鎖住 GM 能改的 state → 沈浸感下降」。

**決策**：把「敘述」和「寫 state」**拆成兩個獨立旋鈕**。玩家**從不**看到 `current_dungeon="鬼滅"`
這行；他看到的是 GM 把入場演得多狠。所以把欄位從 GM 手上鎖走，**敘事一字不少、沈浸感掉 0**。
- 「GM 能敘述多少」→ **開到最大**（沈浸感，免費、無邊界）
- 「GM 能寫多少 state」→ **縮到只剩寫錯也不痛的那層**（正確性）

**關鍵領悟**：寫錯代價最高的東西（記帳）剛好是 GM 來寫對沈浸感**毫無加分**的東西；GM 自由
發揮最能造沈浸感的地方（NPC、世界反應）剛好寫錯也不痛。兩者**負相關** → 邊界自己裂成兩半，
一半鎖死零損失、一半放開低風險。**不是痛苦取捨。**

---

## D3. GM 提議、引擎執行

**脈絡**：就算要確定性，也不想要冷冰冰的死選單，想保留敘事帶出選項的感覺。

**決策**：觸發拆三段，各歸各位——
- **可達性**（這動作現在能不能做）＝**引擎** `available(state)`，永遠在那。
- **浮現**（敘事裡提一嘴誘導）＝GM 寫進 `<!--ACTIONS-->`，best-effort 糖衣，**漏了也沒差**。
- **執行**（真翻 state）＝**引擎** executor，確定性。

**後果**：GM 的角色從「**記得呼叫工具**」（不可靠）降為「**寫出一個選項**」（它的本行）。
GM 不在關鍵路徑上：按鈕的存在不靠 GM（引擎看 state 就掛上面板），GM 漏提也跑不掉。

---

## D4. `available(state)` 可信的前提＝引擎獨佔欄位

**脈絡**：D3 說「引擎依 state 算可達性」，但**state 是誰寫的**？若 `current_dungeon` 還是 GM 寫，
不可靠只是往上搬一層。

**決策**：`available(state)` 讀的**邊界/資源/進度欄位只准確定性轉換寫，GM 在 gate 被 DROP**
（`gate.py` `_ENGINE_OWNED`：`current_dungeon`/`completed_dungeons`/`technique_mastery`/
`technique_days`＋`current_phase` 的 `主神空間/副本中/副本結算`）。引擎路徑直呼 `apply_state_delta`
**繞過 gate**，故鎖只擋 GM、不擋引擎。

**後果**：**「GM 忘了改 current_dungeon」結構上不可能**——改它從來不是 GM 的事；欄位翻動
⟺ 確定性動詞跑過。根治反覆出現的 `current_dungeon` 漏清 ＋ beat-id 汙染 `current_phase`。
GM 仍可敘事驅動 `死亡/傳送中`。

---

## D5. 動詞提前做、名詞 GM 長、新動詞才做 module

**脈絡**：按鈕要不要全部提前備好？

**決策**：一顆按鈕 = **動詞（executor，確定性程式）＋ 名詞（它作用的實例）**。
- **動詞**（機制）：有限、確定性、**提前做**。GM 不能在 runtime 生新動詞（＝寫任意 state，已鎖）。
- **名詞**（實例）：商品/副本IP/功法節點/任務——**GM 在遊戲中用既有動詞生**，資料驅動 UI **自動上架成按鈕**（catalog 加帶 `world` 的 vendor → enter picker 自動多一個 IP）。
- **新動詞 / module**：全新確定性機制（煉丹…）才走四張臉，**YAGNI**。

**後果**：你只需做**少數動詞**，**名詞無限暴漲免費**。配方見 architecture_v2.md §7。

---

## D6. 為何不能「只靠 doc/prompt」——強制執行 > 文件

**脈絡**：問「該做成 tool 的也做一下？還是 doc 就夠？」

**決策**：**doc/prompt 不夠**。這正是整個 v2 的結論：寫在 prompt 的規則是機率性的、會漏；
**該是工具/機制的東西要落進程式碼強制執行**。function-calling 再準也到不了 100%，且失敗靜默
——對「漏掉就壞存檔」的事，任何機率性觸發都不能接受（category error）。

**後果**：本輪把**任務(quest)真的做成模組**（不只寫「應該有任務系統」），dogfood §7 配方 B；
獎勵算術、生命週期、判定一律由引擎。文件描述機制，**機制本身在程式碼裡**。

---

## D7. UI 一致性：遊戲內狀態走「HUD / header-modal」範式；事件不給專屬 widget

**脈絡**：魔潮有一個專屬的 header 倒數 badge；側邊 drawer 又混了「遊戲內狀態（角色狀態/NPC/事件）」
和「session 管理（故事/分支/存檔/設定）」兩種東西，和 v2 的 ⚔🌳💰⚡ header-modal 範式不一致。

**決策**：
- **不給單一內容實例寫專屬 UI**。`魔潮` 是一個 deadline=事件實例；deadline 跟任務一樣是「時間綁定的議程」，
  **統一進同一個 📋 事件/任務 面板**（badge 讀 `label`，不寫死「魔潮」），移除 header 的 `#deadline-display`。
- **遊戲內狀態 = header-modal / 常駐 HUD 範式**（和 ⚔🌳💰⚡ 對齊）：
  - 角色狀態 → **menu bar 常駐 chip**（核心數值：姓名/境界/命運點數嵌在 header，隨時可見）＋點開 `#state-modal` 看完整 schema 詳情。
  - 事件/任務/期限 → 📋 `#events-modal`（一個面板）。
  - NPC → 既有 ⚔ 戰力面板（移除 drawer 重複）。
- **drawer 回歸純 session/app 管理**（故事/分支/存檔/設定／摘要／副本進度）。

**後果**：一種範式、無重複面板、無 per-instance 的 UI 特例。新的遊戲內狀態面板 = 加一顆 header 按鈕 + 一個
modal（資料驅動），和加動作/動詞同樣是「照樣板長一個」。

## 一句話

沈浸感（敘事）開到最大、正確性（state 寫入）縮到引擎獨佔——兩個旋鈕同時轉到底，不打架；
而「該確定性的」一律落進程式碼，不留在 doc/prompt 賭 GM；UI 一種範式，內容實例不另開特例 widget。
